# 问题与目标

本文是 [心智模型](mental-model.md) 定位部分"现在存在什么问题"与"AScout 能做到什么"的展开：先论证为什么需要投机执行、现有工作缺什么，再给出 AScout 的目标。

## 1. 问题陈述

### 1.1 为什么要投机执行

Agent 在执行过程中经常需要等待一个慢结果——远程 API、用户决策、CI 测试。这个慢结果会阻塞后续推理执行，甚至主导整个执行流程：等待期间后续步骤无法推进，端到端延迟被串行的"等 → 再做"主导。

投机执行的目标是把这段等待变成可利用的时间：结果未到时按预测提前推进后续步骤，结果到达后验证预测，保留命中的工作、丢弃未命中的工作，从而以提前执行换取整体执行的加速。投机的收益取决于等待时长、预测命中率与提前工作量的相对大小，这决定了准入与调度必须是机制的一部分，而不是各算法各自处理。

### 1.2 策略孤岛：每种方案只服务一种对象

现有 speculative execution 工作通常针对特定任务和执行对象设计：tool call、plan、function future、workspace branch 各是一套。缺少统一框架来管理预测、验证、隔离、取消和提交，导致方案之间无法组合，也无法让不同的任务选择不同的 policy。

### 1.3 隔离碎片化：隔离范围各不一样

不同方案覆盖的隔离范围不同：有的只能隔离结果或 future，有的能隔离 filesystem、process、memory 或 GUI。对于 network、database、email、payment 等外部副作用，通常只能禁止、延迟或依赖特定 sandbox。缺少一个能够跨任务、跨状态域、跨 speculative policy 统一管理执行与副作用的框架。

### 1.4 上下层脱节：算法与隔离机制之间没有契约

已有工作大多沿两条相对割裂的路径展开：

- 一类关注如何在 Agent 执行中预测并提前执行未来动作，通常通过限制可投机操作类型（read-only、idempotent、sandboxed）来规避副作用风险；
- 另一类关注系统层如何提供状态隔离、分支执行、事务提交或回滚，但没有建模上层投机算法的预测置信度、验证条件和失败代价。

换言之，现有研究缺少一种跨层的 **speculation contract**，把上层算法充分映射到下层执行中。

## 2. 目标

构建一个面向 speculative execution 的通用底座：允许不同任务选择不同的 speculation policy，并统一负责 tentative execution 的**隔离、调度、验证、取消、复用和副作用提交**。

由此达成三个统一：

1. **跨策略**：不同任务可以绑定不同 policy，同一套机制承载多种策略；
2. **跨状态域**：filesystem、process、memory、GUI 以及 network、database、email、payment 由同一套效果管理机制统一处理；
3. **跨层契约**：上层算法与下层隔离机制之间通过显式契约协商，算法作者无需关心底层实现。

设计取舍遵循的原则见 [设计原则](design-principles.md)。
