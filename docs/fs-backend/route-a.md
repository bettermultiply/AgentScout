# 路线 A：挂载命名空间与现有写时复制机制

## 核心思路

使用挂载命名空间为 Agent 进程及其后代进程提供独立的文件系统视图，再使用 OverlayFS、Btrfs、ZFS 或其他现有写时复制机制，将分支写入保存到独立位置。

```text
Agent 进程树
    ↓ 继承
挂载命名空间
    ↓ 使用
分支文件视图
    ├── Parent 创建时的状态
    └── Branch 独立写入位置
```

## 能力来源

- 挂载命名空间负责让同一进程树共享同一个文件系统视图。
- OverlayFS 或文件系统快照负责提供基础状态和独立写入位置。
- Filesystem Backend 负责 Branch 的创建、生命周期、接受、丢弃和清理。
- 当前实现已提供差异生成、冲突检测和 accept 重放；部分接受与物化仍未实现，
  具体状态见 [当前实现状态](current-state.md)。

## 优势

- Agent 不需要修改，也不需要遵守专用文件操作接口。
- 子进程可以通过进程继承自动使用相同视图。
- 文件操作继续使用 Linux 原生文件系统路径，兼容性通常较好。
- 可以利用内核缓存、权限检查和文件锁等现有机制。
- OverlayFS、Btrfs、ZFS 等机制可以降低 Branch 创建和丢弃成本。
- 第一版实现成本和运行时开销相对可控。

## 不足

- 现有机制只提供视图或写时复制，不提供 Branch 的接受、丢弃、冲突和部分合并语义。
- 需要额外设计如何记录或发现 Branch 的文件变化。
- 不同实现对底层文件系统、挂载方式、权限和内核能力有不同要求。
- OverlayFS 的层级数量、挂载范围和特殊挂载点需要额外处理。
- Parent 后续写入对 Child 可见属于额外能力，不会自然获得。

## 第一版定位

第一版采用创建时固定的 Parent 状态。路线 A 提供独立文件视图和独立写入位置；
当前差异生成与 accept 已实现，部分接受仍是后续能力，不由完整 accept 的验证推定完成。
