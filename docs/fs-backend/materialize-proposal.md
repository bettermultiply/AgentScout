# Authority 物化提案（未实现）

## 已确定的责任边界

当前 accept 把结果写入目标环境的 upper；权威环境的写入也停留在各挂载的
upper 中，宿主真实 workspace 不会自动收到这些写入。

物化是可选能力，不在关键路径上。运行阶段物化后重置 authority 的基准；任务
结束即结束 authority 的使命。

控制面只报告操作间隙，例如 Agent 等待用户输入或阶段目标完成后停止活动。
Runtime 根据自身资源、写者和引用情况决定是否以及何时进行内部整理，控制面
不知道物化专用语义。更积极地利用没有存活投机分支的间隙，仍由 Runtime 判断。
“没有存活投机分支”不等于“没有写者”。

本轮只记录上述决定，不新增控制面操作、物化专用确认字段或接口。物化并未实现。

## Runtime 内部仍需明确的实现问题

如果 Runtime 要把 authority upper 的增量写入宿主 Base，必须先确认相关写者
静止、协调宿主侧并发写入，并保证不会污染其它环境仍在引用的 fork/diff 基准。
现有 `Suspended` 或分支数量本身不能替代这些事实的确认。

## 宿主写入要求（待实现）

写宿主文件的方式是写前逐文件与基准比对，再原子替换。比对以 authority base
为共同祖先；来源是 authority 的最终文件系统视图。实现时必须检查性能：先比较
文件大小和修改时间，仅在不一致时再计算哈希。不能只把 upper 的原始目录直接
复制回宿主；删除、opaque、redirect 和 metacopy 需要按 overlay 语义解释。

rename、目录删除等会影响多个路径，必须检测完整受影响路径集合，包括源、目标及
其后代，不能仅比较顶层目录判定无冲突。

## 冲突倾向（尚未最终确认）

冲突倾向让 authority 覆盖，但尚未最终确认；整批失败、等待人工合并或显式选择
覆盖等策略仍未定案。暂不为被覆盖的宿主版本保留可恢复副本，因此不采用此前
journal/备份恢复提案作为现行要求；如果以后重新需要恢复能力，另行设计。

## 边界

accept 的现有语义不变：它只修改目标 Backend 环境，不能隐式写宿主 Base。
未来内部整理也必须保留 Branch 生命周期、single-winner 与 commit/discard
的既有语义。重放到宿主可能使读者看到中间状态，回滚不能自动构成原子性保证；
完整实现和真实环境验证均留待后续。
