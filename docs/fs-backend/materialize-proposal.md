# Authority 物化提案（未实现）

## 已确定的责任边界

当前 accept 把结果写入目标环境的 upper；权威环境的写入也停留在各挂载的
upper 中，宿主真实 workspace 不会自动收到这些写入。

控制面只报告操作间隙，例如 Agent 等待用户输入或阶段目标完成后停止活动。
Runtime 根据自身资源、写者和引用情况决定是否以及何时进行内部整理，控制面
不知道物化专用语义。更积极地利用没有存活投机分支的间隙，仍由 Runtime 判断。
“没有存活投机分支”不等于“没有写者”。

本轮只记录上述决定，不新增控制面操作、物化专用确认字段或接口。物化并未实现。

## Runtime 内部仍需明确的实现问题

如果 Runtime 要把 authority upper 的增量写入宿主 Base，必须先确认相关写者
静止、协调宿主侧并发写入，并保证不会污染其它环境仍在引用的 fork/diff 基准。
现有 `Suspended` 或分支数量本身不能替代这些事实的确认。

下面保留与上述责任边界一致的数据安全提案，作为后续实现和讨论的依据；这些
内容尚未实现，也不代表冲突策略、保留周期或锁契约已经定案。不固定新的操作名、
状态词或控制面确认字段。

## 增量与冲突检测提案（待定）

对每个挂载，以 authority base 为共同祖先、authority 的最终文件系统视图为
source、宿主当前 Base 为 target，先计算 source 相对共同祖先的 delta，再针对
delta 涉及的路径做三方检测。不能只把 upper 的原始目录直接复制回宿主；删除、
opaque、redirect 和 metacopy 需要按 overlay 语义解释。

建议按以下规则检测，具体策略仍待讨论：

- 宿主相对共同祖先未变：可应用 source delta。
- 宿主已变，但与 source 的期望结果相同：可视为已满足。
- 宿主已变，且与 source 不同：报告冲突；默认建议不覆盖、不静默删除宿主内容。
  遇到冲突是整批失败、等待人工合并，还是允许显式选择覆盖，仍待确定；不把
  策略选择绑定为控制面的物化专用接口。
- rename、目录删除等会影响多个路径，必须检测完整受影响路径集合，包括源、
  目标及其后代，不能仅比较顶层目录就判定无冲突。

宿主 workspace 锁和写者协调方案仍待确定。单纯检测无法阻止宿主进程在检查与
写入之间修改文件；实施方案需要覆盖这一时间窗口，并确认其它环境的 fork/diff
基准不受写回污染。

## Journal 与恢复提案（待定）

建议每次会覆盖、删除或移动宿主数据前，先在 journal 中记录原内容和足以恢复的
操作依据；备份可优先 reflink，必要时复制。多挂载需要统一记录已应用的操作顺序。
任何挂载应用失败时，建议按 journal 的逆序恢复全部已应用操作，报告未恢复路径，
而不是只回滚最后一个挂载。

回滚失败时，建议保留 journal、备份及 authority 的相关基准/视图，报告原始错误
和恢复错误，供重试或人工恢复；不能在失败后删除恢复所需依据或宣称宿主已恢复。
成功后何时删除 journal、authority 保留多久以及何时允许释放引用，仍需确定。

accept 的现有语义不变：它只修改目标 Backend 环境，不能隐式写宿主 Base。
未来内部整理也必须保留 Branch 生命周期、single-winner 与 commit/discard
的既有语义。重放到宿主可能使读者看到中间状态，回滚不能自动构成原子性保证；
完整实现和真实环境验证均留待后续。
