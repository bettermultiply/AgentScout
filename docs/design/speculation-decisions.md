# 投机执行底座：设计决策记录

本文件以简短结论定位设计选择，重点记录『为什么』，不重复展开规则。目标语义以对应正式主题文档为准；本文不作为语义权威，也不表示相关能力已经实现。编号只在本文内唯一，跨文件引用必须写文件名加编号；编号不连续，缺号表示该条已落实进正式文档或已废弃。新增条目接续历史最大编号（D-028），不重排历史编号。

本文件与 [设计决策](decisions.md) 是同一系统的两套记录，各自独立编号：后者从 Speculative Tree 机制视角记录，当前最大编号 D-047；本文从投机执行底座视角记录。两者描述同一个 AScout 系统。一级架构以 [AScout 架构](../architecture.md) 为准。

## D-004：Fidelity 在设计中是什么地位？

结论：Fidelity 是导出不变量，不是独立维度。

为什么：Equivalence 是机制层旋钮，Fidelity 是系统层承诺，二者可以独立变化；保真度可从放松匹配、提前释放效果、不启动权威、模型协议退化四条通道丢失。

## D-008：Mechanism / Policy 的线画在哪？

结论：底座只固化正确性机制，策略填决策。

为什么：如果某项工作的机制被迫写进 Mechanism 层，说明抽象漏掉了一个决策维度。

## D-009：多个投机同时在飞且互相依赖时，语义是什么？

结论：未决投机依赖用 AssumptionSet 表达。

为什么：现有工作都没有给出多个未确认投机互相依赖的通用语义；把依赖显式化才能统一级联取消、不一致子树剪枝和坏前缀 kill，并静态限制投机产物进入权威上下文。

## D-010：效果层是只读白名单，还是真正的效果管理？

结论：底座提供真正的效果管理，不止只读白名单。

为什么：多数现有工作只敢投机只读工具；把效果纪律做进 Mechanism 才能把适用范围扩展到可写，并让审计数字由底座而不是单个算法产出。

## D-011：资源与准入进底座吗？

结论：资源准入与调度事实由底座提供。

为什么：投机收益是负载相关的，已有工作证明单个算法在自己的抽象里解决不了准入和调度，因为它们没有调度层。

## D-012：什么算“浪费”？谁定口径？

结论：成本按统一口径三分记账。

为什么：各算法自记账则无法横向比较、无法做全局预算和 kill-switch；口径还必须包含 token 之外的 GPU、并发槽和外部配额，否则拿到的是价目表价格而非真实边际成本。

## D-013：底座是单层还是双层？

结论：底座是单层 orchestration plane，不做推理引擎内部层。

为什么：本系统以 API 方式使用模型，拿不到 KV cache 层 commit、partial-token accept、引擎压力调度等自托管收益；排除这些机制不影响 orchestration plane 的核心抽象，未来自托管时可重新评估。

## D-014：shadow / replay 是四套基础设施吗？

结论：Fidelity 审计、数据管道、成本校准与灰度共用一套 shadow 基础设施。

为什么：四者都需要同一份“投机与串行同跑、只提交串行结果”的影子流量；分别建设会重复造轮子，也无法用同一口径验证 lossless。

## D-015：嵌套投机的拓扑怎么设计？

结论：嵌套投机的成本是速率界，不是组合界。

为什么：分支只在投机或真实调用返回时延伸，不一致子树立即剪枝，因此系统最多领先固定步数，活跃分支数与视界无关；深度和树形属于 Policy，不固化进机制。

## D-016：投机实例知道自己被投机吗？

结论：Agent 业务逻辑不感知自己被投机。

为什么：实例与权威二进制同构是无侵入接入的前提；底座只提供依赖和成本等客观事实，不把 survival 固定为通用字段，也不替 Policy 推断概率。

## D-020：resolve 与调度、效果各归哪个组件？

结论：resolve 并入 Speculation Coordinator，不设独立 Scheduler；效果协调归 Runtime。

为什么：调度与依赖传播必须共用同一份全局视图，两个状态中心会产生不一致；效果状态不属于 Assumption DAG，且图错了只损失性能、效果错了会真的发出邮件。

## D-021：记录类组件是一个还是三个？预算计数器归谁？

结论：只设一个 Ledger；预算计数器归 Coordinator，成本分类归 Ledger。

为什么：预算必须在决策和执行时同步读取，不能挂在异步旁路；成本分类天然发生在 resolve 之后，由协调流程发分类事件、Ledger 存档。

## D-023：虚拟执行（伪造返回值）怎么处理？

结论：不伪造工具返回值。

为什么：伪造值会成为后续行为的条件，即使 L0 全等匹配，轨迹也已建立在编造的 observation 上，破坏点发生在验证机制看不见的地方；若必须模拟，应把模拟值建模成 Proposal，走同一套确认与否定。

## D-024：三条边界并列吗？

结论：Agent Boundary 与 Isolation Boundary 必需，Engine Boundary 不在范围。

为什么：绝大多数 Agent 通过 API 使用模型，控制不了提供方的 KV cache；API 化还使成本问题变严重，并把引擎级收益压缩为塑造请求前缀去命中 cache。

## D-025：为什么需要自研 Runtime？

结论：AScout 需要自己的 Runtime，通用沙箱不够。

为什么：通用沙箱为投机不需要的双向对抗隔离、持久化和 merge 付费，却缺少廉价 COW fork、批量快速销毁、假设感知的效果暂存和确认时的增量状态提升。

## D-026：EffectClass 一维够吗？

结论：效果处理按 EffectClass × StateDomain 二维划分。

为什么：效果纪律描述“怎么处理”，状态域描述“处理哪部分状态”，二者正交；交叉出的每个格子对应一种具体隔离机制，单靠 EffectClass 不足以设计隔离。

## D-027：Fidelity 是单向声明还是双向协商？

结论：Speculation Contract 是双向协商，不是单向声明。

为什么：现有工作一类只管预测与提前执行，另一类只管隔离与回滚，两条路径之间没有契约，多数工作用只读白名单绕开副作用就是缺口的直接证据；双向协商才能回答“给定后端，策略最多能激进到什么程度”。
