# AScout 编码哲学

本文是 AScout 通用的编码与代码审查准绳，适用于后续新增和修改的代码。
按原型阶段的节奏推进即可，无须为了套用风格大规模翻新旧代码。

## 1. 直奔最短路径，性能优先，但避免过早优化

设计结构时，优先选路径直接、耗时低、实现简单的方案。
先关注耗时最多的环节，减少无谓的数据拷贝、跨层搬运，以及不必要的进程启动和沙箱开销。

更简单的实现能满足需求、降低开销时，就选它。
仅为显得规范或预留假想的扩展而增加的层和包装，应当省掉。

局部微优化须有实测依据，先确认瓶颈，再衡量改动收益。
微小的收益不足以抵偿清晰度、通用性或可扩展性的损失。

## 2. 深模块，拒薄壳，控膨胀

模块对外只暴露少量、稳定的接口，在内部完整承担自己的职责。
只转发一两行、没有承担独立职责的包装层应当省掉。

模块内部按职责组织函数，让每一层都容易读懂，避免把几百行杂事堆进同一个函数。
加逻辑前，先看能否简化现有代码，或把新逻辑归入已有结构。

## 3. 消除无意义特例，让主流程自然覆盖边界

遇到空集、首次运行、取消或失败，先检查主流程和数据表示能否自然覆盖这些情况。
例如，遍历空集合本身就会跳过处理，不需要另加一个判断。
取消和失败也应沿既定的状态流转和清理路径处理。

主流程旁不加补丁式的 `if` 特判。
唯一的例外是有实测依据的性能快路径，且它的对外语义必须与常规路径完全一致。

## 4. 保持通用性与可扩展性，同构且对称

横向同构要求不同后端、不同接入产品和同类操作遵循一致的生命周期与接口约定。
具体产品或后端的差异留在各自的实现里，核心层只依赖共同契约。
用清晰统一的契约和深模块承载扩展，避免提前堆砌空壳抽象。

纵向对称要求成对操作在命名、位置和责任上相互对应。
创建与回收、挂载与卸载、暂停与恢复、请求与回执都应做到读懂一边就能推知另一边。

## 5. 控制面核心纯内存推进，其余模块从简

把纯内存推进限定在控制面最核心的状态机，例如 `SpeculativeTree`。
状态机在内存中计算和更新状态，网络、文件和进程读写由外层负责。
这样可减少外部读写阻塞状态流转，也让状态变化更容易追踪。

其余模块按职责直接处理读写，选择清晰、直接的实现。

## 6. 不铺高密度断言，靠结构与不可逆边界守底线

优先用清晰的数据结构与类型约束表达合法状态，让非法状态尽可能写不出来。
日常逻辑避免密集的运行期断言和重复校验。

在极少数不可逆的关键边界保留明确校验。
单赢家晋升前确认只会有一个赢家，物化写回前确认目标是预期的真实工作区，环境资源释放前确认资源归属。
边界校验必须在操作生效前完成，守住不破坏用户真实工作区的底线。

## 代码审查检查清单

- 这条路径是否足够直接，局部微优化是否有实测瓶颈和收益？
- 模块是否以少量接口承担完整职责，新增逻辑能否简化或合并？
- 主流程是否自然涵盖边界情况，性能快路径是否保持相同的对外语义？
- 同类操作是否遵循共同契约，成对操作是否在命名、位置和责任上对应？
- 控制面核心状态机是否在内存中推进，其余模块的读写是否直接清晰？
- 数据结构和类型是否能排除非法状态，不可逆操作是否在生效前通过关键校验？
