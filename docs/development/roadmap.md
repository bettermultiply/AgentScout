# AScout 版本规划

本规划记录已确认的版本目标，属于开发路线，不替代正式设计契约。当前实现尚未达到 v0.1.0；代码中的版本字段不代表里程碑已完成。版本围绕可验证场景组织，各组件共同推进；这里没有承诺工期。

## 总体目标与边界

v1.0.0 的目标是：面向 coding Agent，提供开发者可以实际接入、编写策略并验证收益的通用投机执行底座。开发者能够使用满足要求的 Runtime，表达和组合 Policy，观察执行、验证正确性并比较收益与成本。

以现有投机边和 Policy 抽象为基础，按实际适配证据微调，不预设需要重构整体模型。Policy 的存在形式与编译执行方式需要重新设计，当前 YAML／Python 原型不作为长期方案承诺。

v2 可考虑 CUA 等更广泛 Agent，尚未确定具体交付范围。

## v0.1.0：基本原型与可观察闭环

以 NLE 验证系统可用，并补充一个仅修改文件系统的通用负载投机执行样例。

交付内容：

- 持续可见、原位更新的 NLE 地图和必要的 UI 更新。
- 直观看到候选活动、预测与真实结果、接受／丢弃及清理。
- 人类可读的投机执行成本和开销统计。
- 以 Overlay 为主要实现方式，隔离 Agent 及其后代进程的文件写入，覆盖声明范围内的绝对路径和临时文件。
- 文件操作样例验证候选实际执行、写入不污染其他执行、接受后继续以及丢弃后清理。

验收重点：游戏场景形成基本闭环，文件场景证明真实写入隔离。Overlay 不等于游戏内存复制；当前共享 NLE 世界的候选观察必须如实呈现。具体文件任务、统计指标与验收用例在本版本设计中确定。

## v0.2.0：通用接入与策略控制

在通用任务中验证 Runtime 接入、Policy 控制以及效果管理的共同工作。

交付内容：

- Runtime 的通用接入与 Policy 决策的实际应用、验证完善。
- 重新设计 Policy 的作者接口、表示形式、编译产物及执行方式，不仅更换配置格式。
- 组合与嵌套：假设依赖、父级接受后的后代继续、依赖失效处理等，与 Policy 一起验证。
- 设计并实现好用的 Effect Coordinator，使效果识别、处理计划、Runtime 强制执行、归属、接受／取消与清理形成闭环，提供可理解的诊断与可用的扩展接口。

验收重点：通过 Policy 改变投机行为，接入不同 Runtime 能力，并运行组合／嵌套场景；效果处理确实发生，而不只是记录计划。效果强制处理归 Runtime，控制面保留全局裁决责任。具体支持的效果模式、Runtime 与场景另行确定。

## v0.3.0：验证对齐与可观测性

建立 Policy 要求与 Runtime 实际保证之间的验证闭环，并为论文策略实验提供完整的观察和正确性回放能力。

交付内容：

- Policy 表达、输入输出、决策组合及声明的检查。
- Policy 要求与 Runtime 能力匹配，以及能力声明的实际验证。
- 运行时条件与行为检查、偏差处置、降级／停止和重新验证。
- 明确未知、不支持、未验证及验证失败的区别，区分提前分析、执行前约束与执行后确认。
- 完善观察、事件与历史记录、诊断及正确性回放，并保持 UI 展示与权威事实一致。

验收重点：既能解释为什么允许执行，也能在声明或条件不成立时正确处置；记录足以支持目标范围内的正确性回放。具体静态分析覆盖范围、动态检查点和回放边界需单独设计。

v0.2.0 的效果协调与本版本的验证体系共同参考 [Ahead-of-Time Analysis of Shell Program Effects](https://atlas.cs.brown.edu/pdf/sash:sosp:2026.pdf)。研究其命令效果描述与组合分析方法，不预定直接采用 SaSh；静态分析结果不能替代 Runtime 的实际强制保证。

## v0.4.0：论文策略验证

在共同底座上适配、运行并验证选定的论文投机策略。

交付内容：明确原策略与适配方式、必要的 Policy／模型微调、任务与对照条件，以及可追溯的实验结果。

验收重点：证明策略被正确表达与执行，区分忠实适配、调整和未覆盖部分，建立后续效率比较的基线。具体论文和数量尚未确定，不把先前助手建议的数量视为发布要求。

## v0.5.0：效率优化与发布准备

- **效率**：面向论文方法的比较，按测量结果优化 Policy Engine、控制面及其他实际瓶颈，同时报告任务质量、时间和资源成本。
- **稳定性**：面向系统自身失败，验证超时、取消、组件异常及清理等行为；完整崩溃恢复是否支持另行确定。
- **Agent 接入完整性保证**：在目标 coding Agent 范围内完善会话继续、工具结果、并行工具和 sub-agent 等所需行为，具体支持边界明确列出。
- **发布支持范围补充**：确定支持的 Agent、平台、Runtime、效果模式与使用方式，补齐安装、配置、接入、诊断及复现文档。

验收重点：性能比较可解释，失败行为可靠，所声明的接入与使用范围经过验证。效率测量和必要故障修复贯穿此前版本，本版本集中完成优化和验收。

## v1.0.0：通用底座正式发布

在上述阶段完成后发布。开发者能够实际接入、编写策略并验证收益；支持范围、使用方式、保证和限制清楚，运行与实验可以复现。不承诺所有任务普遍加速。

## 贯穿开发的要求

- 降低验证成本是整个开发生命周期的约束，不是单独的版本交付目标。多步行动、上下文压缩及 trace 回放均可按需要采用。
- 廉价回放用于修改代码过程中的正确性验证，不作为真实模型质量或实际性能收益的证据。
- 跨组件操作一致性属于天然必须满足的正确性要求，不单列为整体规划工作方向。
- 每阶段落实相应正确性与效果边界，不能把必要保障推迟到集中完善版本。
- 各版本的具体方案、任务、量化阈值和验收清单逐步细化，不在整体规划中提前固定。
