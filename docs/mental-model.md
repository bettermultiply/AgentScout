# AScout 心智模型

> 本文是理解 AScout 的起点：先给出 AScout 的定位（定义、问题、目标、边界），再介绍它的工作模型及其支撑模型。本文只记录已经确定的目标语义；问题与目标的完整论证见 [问题与目标](problems-and-goals.md)，设计原则见 [设计原则](design-principles.md)，逐条决策的权威出处见 [设计决策](design/speculation-decisions.md) 与 [状态与生命周期语义](design/overview.md)，系统结构见 [架构](architecture.md)。

## 1. 定位

AScout（Agent Scout）是面向 Agent 投机执行的通用底座：将投机执行所需的多种能力抽象为统一机制，使开发者能够通过组合与替换这些能力，构建出不同的执行策略。

投机执行想要解决的问题是：Agent 在执行过程中经常需要等待一个慢结果——远程 API、用户决策、CI 测试——它会阻塞后续推理执行，甚至主导整个执行流程。投机执行允许在结果尚未到达时按预测提前推进后续步骤，从而加速整个执行过程；而它所依赖的预测、验证、隔离、取消、复用与副作用提交，正是 AScout 抽象为统一机制的那组能力。

现有投机执行工作大多针对特定执行对象（tool call、plan、workspace branch）或特定状态域设计，能力与任务绑定，方案之间无法组合，也无法让不同任务选择不同策略。这些问题集中表现为三个缺口——策略孤岛、隔离碎片化、上下层脱节，具体论证与 AScout 的目标在 [问题与目标](problems-and-goals.md) 中展开。

AScout 的能力体现在三个层面。
- 策略层：任意算法都可以作为一条 policy 接入，预测器、等价判定、拓扑、成本、补偿等特征可独立替换、组合，并按任务选择。
- 状态域层：文件系统、进程、内存、GUI 以及 network、database、email、payment 等外部状态域，由同一套效果管理机制统一处理，不必为每种状态域另建隔离与副作用方案。
- 契约层：上层算法与下层隔离机制通过 Speculation Contract 双向协商——上层声明预测置信度、验证条件与失败代价，下层声明隔离能力、隔离代价与可用纪律。

落在使用上：
- 端用户提交任务、得到结果，无需感知背后的投机分支；
- Agent 开发者接入后不必重写执行逻辑；
- 部署方（Operator）按部署需要选择 policy 与隔离后端、设定预算；
- Policy 作者只需专注于算法设计（如何预测、如何判定命中、如何选择拓扑与成本），无需关心底层隔离与能力如何实现——这些由底座统一提供。

AScout 不是某个固定算法，也不承诺每个任务必然加速；是否投机、如何投机由控制面根据所绑定的 Policy 决定，投机与否本身就是 Policy 的决策内容。

## 2. AScout 的工作模型

### 2.1 投机执行过程

具体而言，一次投机执行可以描述为以下运行流程。

当 Agent 正在进行某一特定行为时，这一行为（称为**权威行为**）会被捕获并触发投机执行系统。系统首先根据 Agent 当前状态、系统资源条件和投机执行深度等因素，判断当前是否适合进行投机执行。

当判定适合投机时，系统预测权威行为的 N 个可能结果，并将这些结果视作后续行为的输入。据此创建 N 个投机执行过程并运行——这些过程彼此隔离，互不影响，也不影响 Agent 已有行为的执行。

当权威行为完成时，系统将权威结果与各预测结果进行对照，从中选择至多一个（也可以一个都不选）作为匹配结果。不匹配的投机执行过程被终止并回收；匹配的过程则复用其结果。至此，一次投机执行结束。

需要注意：上述流程只描述**单一投机执行过程**的最小工作模型；当嵌套投机等复杂行为共同作用时，系统完整流程由多个这样的最小过程组合而成，并不限于这一线性描述。

投机执行由一组可组合的阶段构成，而不是固定的线性流程。Policy 可以根据任务、执行对象、可用信息和 Runtime 能力选择其中的阶段，并决定各阶段的具体实现与组合方式。某些阶段可以缺失，但被启用的阶段仍需遵守必要的数据依赖和 AScout 固定的正确性、隔离、资源与副作用约束。

一个投机执行过程可以总结为以下阶段：机会发现 -> 准入判断 -> 预测生成 -> 过程执行 -> 验证 -> 处置与提交

具体来说

1. **机会发现**：按照 Policy 规定的方式观察 Agent 或其他执行对象，在检测到特定类型的行为、命令或执行步骤时，识别潜在的投机机会。
2. **准入判断**：由 Policy 判断当前机会是否适合投机，并综合考虑效果类型、资源条件、预测条件、隔离能力和预期收益。
3. **预测生成**：产生一个或多个 Proposal，为后续投机工作提供暂时依据。Proposal 可以来自模型、规则、历史轨迹、外部系统或其他来源。
4. **过程执行**：基于 Proposal 提前执行投机工作。投机工作可以是模型推理、工具调用、命令执行、远程请求或其他计算。
5. **验证**：获取用于验证 Proposal 的权威依据，并按 Policy 规定的条件判断 Proposal 是否兼容或达到可接受标准。权威依据可以来自真实执行、用户输入、环境反馈、远程服务或 validator；没有权威依据时，验证改用 validator 或其他可接受性判断。
6. **处置与提交**：根据验证结果复用、继续、取消、重新执行、清理、残值回收、补偿或以其他方式处理投机工作，并将符合条件的结果、状态变化和外部效果纳入后续执行；没有需要提交的结果或副作用时，可以不设置独立的提交阶段。

这些阶段在职责和实现上相互独立，Policy 可以选择、替换和组合它们，但并不意味着阶段之间没有任何关系。例如，基于 Proposal 的投机工作需要先获得某种暂时依据；没有权威依据时，验证必须改用 validator 或其他可接受性判断；结果和副作用在满足相应条件前不能进入最终执行状态。Policy 决定执行策略，Mechanism 保证策略在既定约束内执行。

### 2.2 投机边：投机执行的最小结构模型

可以对一次投机执行过程进行进一步抽象。将 Agent 的一整个任务的执行过程都描述为一个执行图，原行为为起始点。每发生一次投机执行过程就在像树一样从点上延伸出多个子节点，子节点之间无边，节点之间的连线被称为投机边。边的起点 `u` 代表一个会产生结果的行为，终点 `v` 对应依赖该结果才能继续的后续行为。当起点的结果 `i` 尚未确定时，系统可以先对结果进行预测，用预测值 `î` 替代 `i`，让终点暂时依据预测继续执行。`i` 确定时对边进行有效标记，代表验证通过选择某条投机边成为现实。

N 个预测就是 N 条并行的边。因此投机边描述“哪个结果尚未确定”以及“哪个后续工作可以提前执行”，可以统一表示模型推理、命令执行、工具调用、远程请求和其他计算——它们的差异只是边的两端的行为对应什么、谁提供权威依据、投机工作是什么，以及各自需要什么隔离和效果处理能力；投机过程本身不需要为每一种对象重新定义一套基本流程。

### 2.3 组合与嵌套

嵌套投机就是边的串联：下游投机建立在若干上游未验证的投机边之上，因此它是否成立取决于这些上游边。每条投机边隐含一个未验证前提——"预测值 `î` 成立"；一条路径携带的前提，是它沿途所有未验证边的前提之并集。权威结果确定时，验证决定这些前提的去留：匹配则那条边成为现实，依赖它的下游边随之少一个前提，前提清空的那条就地转正为权威路径；不匹配则建立在错误前提上的整条后续链整体失效，进入回收或丢弃，不做逐个修补。由此得到一条信息流约束：未验证路径产生的数据不能进入权威路径，只能经验证这一步流入，避免投机产物污染权威上下文。

### 2.4 抽象分层

Policy、Mechanism 与 Runtime 构成三层抽象，逐层向上提供更抽象的接口：

```
Policy（抽象接口：作者只需面对决策点）
   ↓
Mechanism（实现层：拦截、执行、隔离、资源、效果、调度）
   ↓
Runtime（具体后端原语）
```

**Policy：作者只需面对抽象。** Policy 作者面对的是一组抽象的决策点——在哪些环节投机（推理、工具执行等）、预测什么、如何判定命中、用什么公式判断是否值得投机、如何展开与处置投机工作。作者只需要给出这些决策的实现或选择，不需要知道系统是怎么落实的：命令如何被拦截、隔离环境如何创建、资源如何管理、失败分支如何清理，都由 Mechanism 负责。分层把"作者可以灵活定制"的部分与"必须可靠执行"的部分分开：作者在算法层面自由选择，正确性、隔离与资源约束由 Mechanism 兜底。

**Mechanism：把抽象落实为执行。** Mechanism 是抽象的实现层，横跨多个部分：在 Agent 接入侧通过 Interposer 拦截命令与推理调用等环节，在控制面组织执行、验证与调度，在 Runtime 落实隔离、资源与效果管理。它不一定是组合 Runtime 原语——拦截、效果管理、调度等能力本身就是 Mechanism 的一部分；后端缺失所需原语时，降级或拒绝，不让策略悄悄跑偏。

**Runtime：只提供简单原语。** Runtime 是具体执行后端，只负责上报并执行一组简单原语，不实现组合逻辑。原语本身是稳定的抽象、各后端保持一致兼容，换后端只换原语的实现——不换原语、不换组合。Adapter 侧的工作因此很简单：翻译调用 + 上报原语清单。

**Speculation Contract：静态与动态保证抽象分层匹配、约束满足。** 作者写算法时声明需求（预测置信度、验证条件、失败代价、需要的隔离与效果纪律），具体 Runtime 通过 Adapter 上报自己的能力。Speculation Contract 在加载期静态校验需求与能力是否匹配，不匹配就拒绝或降级；在运行期由 shadow 实测声明的保真度是否真的达成。它保证抽象分层两侧始终对齐，并确保正确性、保真度等固定约束被满足——作者只需声明需求，不必知道后端实现。

## 3. 支撑模型

### 3.1 Policy Decisions

Policy Decision 是 Policy 可以根据任务、上下文、资源和 Runtime 能力作出的可替换决策。以下内容是当前投机执行中最重要的代表性阶段决策及导出属性，并非穷尽列表；更完整的 Policy 决策面见 [Policy Decisions 设计](design/policy-decisions.md)。

| 阶段中的代表性决策 | 管什么 |
|---|---|
| 准入与权威启动 | `A_u` 跑不跑、何时跑 |
| 拓扑展开与投机执行 | 投机树的宽度与深度 |
| 预测生成 | 怎么猜 `î` |
| 权威获取与验证 | 谁产出依据 `i`，以及如何判断兼容 |
| 处置与提交 | 真值到达后怎么处理投机结果 |
| Fidelity（导出属性） | 系统层承诺的保真等级 |

机会发现与 Site 注册是这些决策的前置接缝，不属于上述六项中的独立 Policy Decision。EffectClass、资源准入和 Speculation Contract 是决策可行性的约束与输入，不是固定数量的 Policy Decision。Policy 可以继续增加决策项，但不能违反 AScout 的固定语义和 Mechanism 约束。

### 3.2 状态与效果

不同投机方案往往只能隔离某一种状态或某一类产物，这正是隔离碎片化的问题。状态与效果模型把投机执行产生的文件、进程、输入、结果和外部服务交互放入统一的管理框架，并根据状态域和效果纪律选择相应的隔离、暂存、延迟释放、补偿或清理方式。

投机产物在验证、提交和必要的状态转换完成前不能进入最终语义状态。无法安全隔离、延迟释放或补偿的效果必须拒绝投机或降级处理。具体的 `EffectClass × StateDomain` 分类、交叉规则和 Runtime 实现见 [副作用管理](design/effect-management.md)。

控制面中的 Effect Coordinator 负责效果分类、计划与协调；Runtime 负责 staged effect、obligation、materialization、隔离和清理等状态。前者形成控制计划，后者负责实际执行和强制，两者之间不能互相越权。

### 3.3 Speculation Contract

Policy 与 Runtime 分别解决“如何选择投机”和“如何可靠执行”的问题，但如果两者各自设计，就会形成上下层脱节。Speculation Contract 是连接两者的共同语言：Policy 声明预测置信度、验证条件和失败代价，Runtime Adapter 声明隔离能力、隔离代价和可用纪律，Mechanism 作为连接二者的桥梁。

首先是可协商的跨层能力：

- Policy 声明预测置信度、验证条件和失败代价；
- Runtime Adapter 声明隔离能力、隔离代价和可用纪律；
- Contract 在加载期校验两侧是否匹配，不可行的组合必须拒绝或明确降级；
- 运行期通过权威结果、validator 和必要的 shadow/replay 反馈校准实际行为。

Contract 不能被理解为放宽 AScout 固定语义的协商机制。所有合法的 Policy、Runtime Adapter 和 Runtime 都必须共同服从以下三类固定语义底线：

1. **控制语义**：Branch 通过 `branch`、`commit`、`accept` 和 `discard` 演化；Proposal 在验证前只是未验证前提，未解决的 obligation 随 subtree 保留；一次裁决至多接受一个 candidate subtree，不做多个候选世界的通用 merge；未满足验证条件时不能 `accept`。
2. **世界状态与效果语义**：Branch 的 local state、进程内存和 Agent context 默认彼此隔离；跨 Branch 信息必须经过显式受控通道，未验证路径产生的数据不能流入权威上下文；投机效果在满足验证、提交、隔离、延迟释放或补偿条件前不能进入最终语义状态，无法安全处理的效果必须拒绝投机或降级。
3. **执行边界与资源所有权**：Runtime 拥有节点执行状态、进程与资源归属、隔离和 cleanup，并强制 identity、capability、barrier、原子状态转换、抢占、取消和 loser cleanup；控制面拥有控制语义但不能直接修改 Runtime 状态，Runtime Adapter 负责跨层映射但不能改变 Policy 或生命周期语义。

详细生命周期、状态可见性和效果规则见 [状态与生命周期语义](design/overview.md) 与 [设计决策](design/decisions.md)。Fidelity 是这些决策与能力共同导出的系统级属性；shadow/replay 是验证和校准基础设施，而不是另一个独立模型。

## 4. 系统结构

### 4.1 四侧架构

AScout 按以下四侧组织，控制请求向下流动，结果与事件向上返回：

```text
Agent 接入侧 -> 控制面 -> Runtime Adapter -> Runtime
```

四侧是逻辑责任边界，不等同于四个进程或 crate。各侧的所有权和边界见 [架构](architecture.md)。

控制请求沿四侧向下传递，结果和事件沿相反方向返回：

```text
Policy Action -> 控制面编排 -> Runtime Adapter 映射
  -> Runtime 执行 -> typed result/event -> 控制面更新控制状态
```

### 4.2 核心对象与所有权

`task` 是 session 中一次独立的 AScout 管理单元。AScout 为每个 task 建立一个 AScoutAgent 控制域，并在其中维护一棵 Speculative Tree。

```text
task
  -> AScoutAgent
      -> Speculative Tree
          -> Branch
              -> Branch Node
                  -> Instance
```

task 准入时绑定 policy profile，并建立初始 Agent，称为 root Authority Instance。在运行过程中，随着投机执行的不断发生和结束，Authority Instance 不断变化，由此形成树形结构。树中的每个子树都称为 `Branch`。`Branch` 是树中的计算延续，也是投机世界的结构实体；Branch 对应的根节点称为 `Branch Node`。`Instance` 是 Runtime 中承载 Node 的实际执行单元，代表实际运行的单一 Agent。

对外，为只呈现一个单一 Agent，这个统一视图称为 `AScoutAgent`。它拥有 Speculative Tree 的控制状态和 Branch 之间的关系。由此，一个 task 对应一个 AScoutAgent，一个 AScoutAgent 拥有一棵 Speculative Tree；控制面拥有 Tree、Branch 关系和控制状态，Runtime 拥有 Instance 的执行、资源和隔离状态。
