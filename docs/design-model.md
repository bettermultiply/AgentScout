# 设计模型

本文指导 AScout 的**抽象概念层**：它描述策略如何被表达、机制如何落实、运行能力如何支撑，不描述具体系统如何部署与连线。本文与架构是 mental-model 的两个平级展开，分别对应心智模型中的工作模型与支撑模型（§2、§3）。

本文只记录已确定的抽象语义。仓库当前没有实现；开发决策、路线图与验收状态记录在开发文档中。

## 1. 抽象分层：Policy / Mechanism / Runtime

Policy、Mechanism 与 Runtime 构成抽象责任模型，描述从策略意图到机制落实、再到具体运行能力的关系。

```
Policy（抽象接口：作者只需面对决策点）
   ↓
Mechanism（实现层：拦截、执行、隔离、资源、效果、调度）
   ↓
Runtime（具体后端原语）
```

图中的箭头表示抽象关系从策略意图向运行能力落实，不表示系统调用方向或能力提供方向。

**Policy：作者只需面对抽象。** Policy 作者面对的是一组抽象的决策点——在哪些环节投机（推理、工具执行等）、预测什么、如何判定命中、用什么公式判断是否值得投机、如何展开与处置投机工作。作者只需要给出这些决策的实现或选择，不需要知道系统是怎么落实的：命令如何被拦截、隔离环境如何创建、资源如何管理、失败分支如何清理，都由 Mechanism 负责。分层把"作者可以灵活定制"的部分与"必须可靠执行"的部分分开：作者在算法层面自由选择，正确性、隔离与资源约束由 Mechanism 兜底。

**Mechanism：把抽象落实为执行。** Mechanism 是抽象的实现层，横跨多个部分：在 Agent 接入侧通过 Interposer 拦截命令与推理调用等环节，在控制面组织执行、验证与调度，在 Runtime 落实隔离、资源与效果管理。它不一定是组合 Runtime 原语——拦截、效果管理、调度等能力本身就是 Mechanism 的一部分；后端缺失所需原语时，降级或拒绝，不让策略悄悄跑偏。

**Runtime：只提供简单原语。** Runtime 是具体执行后端，只负责上报并执行一组简单原语，不实现组合逻辑。原语本身是稳定的抽象、各后端保持一致兼容，换后端只换原语的实现——不换原语、不换组合。Adapter 侧的工作因此很简单：翻译调用 + 上报原语清单。

**Speculation Contract：静态与动态保证抽象分层匹配、约束满足。** 作者写算法时声明需求（预测置信度、验证条件、失败代价、需要的隔离与效果纪律），具体 Runtime 通过 Adapter 上报自己的能力。Speculation Contract 在加载期静态校验需求与能力是否匹配，不匹配就拒绝或降级；在运行期由 shadow 实测声明的保真度是否真的达成。它保证抽象分层两侧始终对齐，并确保正确性、保真度等固定约束被满足——作者只需声明需求，不必知道后端实现。

## 2. 工作模型

### 2.1 投机执行过程

投机执行的最小条件，是后续工作暂时依赖一个尚未确认的 Proposal，并且之后存在能够验证或接受这个 Proposal 的依据。这个依据可以来自 Authority 提供的真实结果，也可以来自独立 validator 给出的可接受性判断。

等待真实结果是其中最常见的一类。此时，当 Agent 正在进行某一特定行为时，这一行为会被捕获并触发投机执行系统。系统首先根据 Agent 当前状态、系统资源条件和投机执行深度等因素，判断当前是否适合进行投机执行。

当判定适合投机时，系统预测该行为的 N 个可能结果，并将这些 Proposal 暂时视作后续行为的输入。据此创建 N 个投机执行过程并运行——这些过程彼此隔离，互不影响，也不影响 Agent 已有行为的执行。

Agent 默认无需感知背后的投机分支，仍可按原方式完成任务。对于需要显式协作的 Agent，AScout 可以提供受控的感知、查询、提示和协作入口，使 Agent 参与候选创建或裁决等工作；这些入口最终仍受控制面与 Runtime 的身份、能力、single-winner、隔离和清理约束，不能成为生命周期正确性的绕行路径。

当真实结果到达时，系统将它与各 Proposal 对照，从中选择至多一个兼容的过程。不兼容的投机执行过程被终止并回收；兼容的过程则复用其结果。如果不存在需要并行运行的权威行为，系统也可以依据独立 validator 判断 Proposal 是否达到可接受标准。至此，一次投机执行结束。

需要注意：上述"等待真实结果"的流程是典型流程，不是投机执行的普遍前提；当 Authority 为空、阶段被替换或省略，或者嵌套投机等复杂行为共同作用时，系统流程并不限于这一线性描述。

投机执行由一组可组合的阶段构成，而不是固定的线性流程。Policy 可以根据任务、执行对象、可用信息和 Runtime 能力选择其中的阶段，并决定各阶段的具体实现与组合方式。某些阶段可以缺失，但被启用的阶段仍需遵守必要的数据依赖和 AScout 固定的正确性、隔离、资源与副作用约束。

一个投机执行过程可以总结为以下阶段：机会发现 -> 准入判断 -> 预测生成 -> 过程执行 -> 验证 -> 处置与提交

1. **机会发现**：在 Agent 接入侧识别并规范化 operation 及其 `pending-result boundary`，按照 Policy 规定的方式登记潜在的投机 Edge。具体的命令拦截、Hook、CLI、embedded adapter 或进程观察方式属于接入实现，不是投机执行的固定前提。
2. **准入判断**：由 Policy 判断当前机会是否适合投机，并综合考虑效果类型、资源条件、预测条件、隔离能力和预期收益。
3. **预测生成**：产生一个或多个 Proposal，为后续投机工作提供暂时依据。Proposal 可以来自模型、规则、历史轨迹、外部系统或其他来源。
4. **过程执行**：基于 Proposal 提前执行投机工作。投机工作可以是模型推理、工具调用、命令执行、远程请求或其他计算。
5. **验证**：获取用于验证 Proposal 的权威依据，并按 Policy 规定的条件判断 Proposal 是否兼容或达到可接受标准。权威依据可以来自 Authority 提供的真实执行、用户输入、环境反馈或远程服务；Authority 可以为空，此时由独立的 validator 或其他可接受性判断完成验证。
6. **处置与提交**：根据验证结果复用、继续、取消、重新执行、清理、残值回收、补偿或以其他方式处理投机工作，并将符合条件的结果、状态变化和外部效果纳入后续执行；没有需要提交的结果或副作用时，可以不设置独立的提交阶段。

这些阶段在职责和实现上相互独立，Policy 可以选择、替换和组合它们，但并不意味着阶段之间没有任何关系。例如，基于 Proposal 的投机工作需要先获得某种暂时依据；没有权威依据时，验证必须改用 validator 或其他可接受性判断；结果和副作用在满足相应条件前不能进入最终执行状态。Policy 决定执行策略，Mechanism 保证策略在既定约束内执行。

### 2.2 投机边 Edge

可以对一次投机执行过程进行进一步抽象。将 Agent 的一整个任务的执行过程都描述为一个执行图，原行为为起始点。每发生一次投机执行过程就在像树一样从点上延伸出多个子节点，子节点之间无边，节点之间的连线被称为投机边。边的起点 `u` 代表一个会产生结果的行为，终点 `v` 对应依赖该结果才能继续的后续行为。当起点的结果 `i` 尚未确定时，系统可以先对结果进行预测，用预测值 `î` 替代 `i`，让终点暂时依据预测继续执行。`i` 确定时对边进行有效标记，代表验证通过选择某条投机边成为现实。

N 个预测就是 N 条并行的边。因此投机边描述"哪个结果尚未确定"以及"哪个后续工作可以提前执行"，可以统一表示模型推理、命令执行、工具调用、远程请求和其他计算——它们的差异只是边的两端的行为对应什么、谁提供权威依据、投机工作是什么，以及各自需要什么隔离和效果处理能力；投机过程本身不需要为每一种对象重新定义一套基本流程。

**一条投机边的核心模型。** 执行图中每条被标注为"可投机"的依赖边记为 `u → v`，其中 `v` 消费 `u` 的输出 `i`。当 `i` 尚未由权威路径产出时，AScout 用预测值 `î` 替代 `i` 启动 `v`，这条边就构成一次投机执行。一条边上并存两个实现：

- **权威实现 `A_u`**：产出真实结果 `i`。是否启动、何时启动是策略决策，不是模型的固有属性；
- **投机实现 `S_u`（Predictor）**：产出预测值 `î`。

权威结果到达时执行 **Reconciliation**：判定 `î ≈ i` 并选择 **Disposition**。等价关系与处置结果见 [Policy Decisions 设计](design/policy-decisions.md)。

一条投机边涉及六个实体（一句话定义见 [术语表](design/glossary.md)）：

| 实体 | 定义 |
|---|---|
| **Edge** | 图上一条被标注为"可投机"的依赖边 `u → v`，携带 admissibility 元数据；投机启动点的结构表示 |
| **Proposal** `î` | 一次预测值 `{value, confidence, provenance, source}`；候选 Branch 基于它提前执行 |
| **SpecTask** | 基于 `î` 启动的投机工作单元，运行在隔离域中，携带 AssumptionSet；对应 candidate Branch |
| **Authority** `A_u` | 提供真实输入、结果或外部权威判断的可选来源；可以为空，此时由 validator 作可接受性判断 |
| **Reconciliation** | 权威到达时判定 `î ≈ i` 并选择处置的过程；对应 Resolution barrier 的验证部分 |
| **Disposition** | 处置结果的枚举 |

三个层次不重叠：**Proposal** 是 orchestration 层的投机值；**Assumption** 是依赖图上表示"某 Proposal 成立"这一未验证前提的边（见 2.3）；**Draft** 是 engine 层的 token 级草稿，不用于 orchestration 层的值。

### 2.3 组合与嵌套

嵌套投机就是边的串联：下游投机建立在若干上游未验证的投机边之上，因此它是否成立取决于这些上游边。每条投机边隐含一个未验证前提——"预测值 `î` 成立"；一条路径携带的前提，是它沿途所有未验证边的前提之并集。验证依据确定时，验证决定这些前提的去留：兼容或可接受时，那条边成为现实，依赖它的下游边随之少一个前提，前提清空的那条就地转正为权威路径；不兼容或不可接受时，建立在错误前提上的整条后续链整体失效，进入回收或丢弃，不做逐个修补。由此得到一条信息流约束：未验证路径产生的数据不能进入权威路径，只能经验证这一步流入，避免投机产物污染权威上下文。

**前提的形式化：Assumption DAG。** AScout 把每个前提建模为一个 Assumption：

```
Assumption     = (edge_id, proposal_id)
AssumptionSet  = frozenset[Assumption]    # 工作单元携带的依赖闭包
```

规则：

- `AssumptionSet == ∅` ⟺ 该工作单元是权威工作；
- 某 assumption 被 **confirm** → 从所有工作单元的 set 中移除；set 变空的工作单元可以 commit；
- 某 assumption 被 **refute** → 依赖它的整个子图进入 Salvage → Discard；
- 投机工作单元之间**可以**互相依赖（推测链），set 做并集。

由此得到一条可静态检查的**信息流约束**：非空 AssumptionSet 产生的数据只能流向同样非空的容器，唯一降级通道是验证。底座能强制它，单个算法做不到。

**嵌套投机。** 实例视角下，一次投机会并行运行多个 Agent 实例；每个投机实例执行的步骤"就是正经执行"，因此它自己也可以继续投机——这就是嵌套。边视角与实例视角由 AssumptionSet 连接：边引入一个 Assumption，实例携带其路径上所有边引入的假设之并，`AssumptionSet == ∅` ⟺ 权威实例。

**透明嵌套与反射 gating。** 投机实例与权威实例二进制同构，Agent 业务逻辑与 Predictor 都不知道自己是投机的（透明）；但 Cost/admission 策略必须知道，底座需要透传 `P(实例存活)`（反射），否则深度投机实例会按深度 0 的账过度投机。这是对 gating 的改动，不是对算法行为逻辑的改动。

**嵌套拓扑的成本与形态。** 分支只在投机或真实调用返回时才延伸、不一致子树立即剪枝，因此活跃分支数与执行视界无关，成本是速率界而非组合界。depth 不是策略参数，而是在 frontier budget 下按优先级涌现的属性；浅层分叉、深层单链是划算的形态——每层存活率被浅层 breadth 推高后，深度才可行。

## 3. 支撑模型

### 3.1 Policy Decisions

Policy Decision 是 Policy 可以根据任务、上下文、资源和 Runtime 能力作出的可替换决策，通过对不同 Policy Decision 的组合可以生成不同的执行策略。以下是当前投机执行中最重要的代表性阶段决策及导出属性，并非穷尽列表：

| 阶段中的代表性决策 | 管什么 |
|---|---|
| 准入与权威启动 | 权威行为跑不跑、何时跑 |
| 拓扑展开与投机执行 | 投机树的宽度与深度 |
| 预测生成 | 怎么猜 `î` |
| 权威获取与验证 | 谁产出依据 `i`，以及如何判断兼容 |
| 处置与提交 | 真值到达后怎么处理投机结果 |
| Fidelity（导出属性） | 系统层承诺的保真等级 |

机会发现与 Edge 注册是这些决策的前置接缝，不属于上述六项中的独立 Policy Decision。EffectClass、资源准入和 Speculation Contract 是决策可行性的约束与输入，不是固定数量的 Policy Decision。Policy 可以继续增加决策项，但不能违反 AScout 的固定语义和 Mechanism 约束。完整的决策面与阶段映射见 [Policy Decisions 设计](design/policy-decisions.md)。

### 3.2 状态与效果

不同隔离方案往往隔离粒度不同，且较为全面的方案未对投机执行进行专门的适配，投机执行算法提出的方案都较为简单。并且都没有提供统一的接入方式，适配工作量大，这正是隔离碎片化的问题。状态与效果模型把投机执行产生的文件、进程、输入、结果和外部服务交互放入统一的管理框架，提供统一的接入方式，并根据状态域和效果纪律选择相应的隔离、暂存、延迟释放、补偿或清理方式。

投机产物在验证、提交和必要的状态转换完成前不能进入最终语义状态。无法安全隔离、延迟释放或补偿的效果必须拒绝投机或降级处理。具体的 `EffectClass × StateDomain` 分类、交叉规则和 Runtime 实现见 [效果管理设计](design/effect-management.md)。

控制面中的 Effect Coordinator 负责效果分类、计划与协调；Runtime 负责 staged effect、obligation、materialization、隔离和清理等状态。前者形成控制计划，后者负责实际执行和强制，两者之间不能互相越权。

### 3.3 Speculation Contract

Speculation Contract 的目的，是把一个投机策略成立所依赖的前提变成可检查的契约，避免策略在不具备必要能力的 Runtime 上被静默执行，也让降级原因对使用者可见。

根据 Policy 注册时声明和 Runtime Adapter 声明，控制面在加载或任务准入时对两组声明进行约束检查，生成已验证的 policy profile；无法满足的组合必须拒绝，或明确标记为降级。运行期间记录 Authority、validator 和效果处理的实际结果，并用动态检查声明的要求是否达到。

Contract 只描述并检查策略与执行能力之间的匹配关系，不重新定义 AScout 的目标语义。具体的契约字段、校验流程、降级结果和运行期审计见 [Speculation Contract 设计](design/speculation-contract.md)。

## 4. 跨领域设计约束

以下约束适用于 Policy、Mechanism、Runtime 及其扩展的设计取舍：

1. **策略选择不应被机制固化**：能够交给 Policy 选择的内容，不应由核心机制或 Runtime 固定。
2. **正确性与资源所有权不能依赖策略自律**：必须由 AScout Mechanism 或 Runtime 强制的约束，不能只依赖 Policy 遵守。
3. **跨层语义必须显式表达**：Policy 的要求、Runtime 的能力和运行结果不能依赖未声明的隐含假设。
4. **能力不足不得静默改变语义**：只能拒绝、明确降级或选择其他合法路径。
5. **扩展不能破坏既有固定语义**：新 Policy、Runtime、状态域或其他扩展不能绕过 Branch、single-winner、隔离、obligation 和 cleanup 等固定约束。
